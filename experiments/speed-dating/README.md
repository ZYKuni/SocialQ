# 匹配验证实验：Agent 代聊能预测两个真人合不合得来吗？

SocialQ 的核心假设是：**让双方的 AI 分身先代聊几句，就能判断两个真人是否值得认识。**
这个假设决定了产品成不成立，所以在写更多功能之前，先用真实数据检验它。

## 1. 要回答的问题

| 编号 | 问题 | 对应比较 |
|---|---|---|
| H1 | 只凭见面前的信息，能不能预测两个人见面后会互相有兴趣？ | 所有方法 vs 随机（AUC 0.5） |
| H2 | 大模型读档案，是否比规则和机器学习判断得更准？ | L1 vs B1、B2 |
| H3 | **代聊这一步有没有带来档案之外的信息？**（SocialQ 最关键的假设） | L2-judge vs L1 |

## 2. 数据

- 来源：哥伦比亚大学快速约会实验（Fisman, Iyengar, Kamenica & Simonson, 2006），2002–2004 年共 21 场活动、551 人、8378 条约会记录。
- 每对约会 4 分钟，结束后双方各自决定 Yes / No。**标签 = 双方都选了 Yes（互选成功）**。
- 清洗后：问卷完整的 538 人，4017 对可用配对，互选成功率 16.3%。
- 评测集：分层抽样正负各 150 对，共 300 对（随机种子固定）。AUC 不受正负比例影响，平衡抽样能用更少的调用得到更窄的置信区间。

## 3. 防止“作弊”的设计

1. **只用见面前的信息**：只用报名问卷（年龄、专业、职业、来参加的目的、约会/外出频率、17 项兴趣打分、择偶时看重什么、自我评价）。见面时的打分、决定、事后回访一律不用。
2. **信息对等**：规则、机器学习、大模型用的是同一份档案。
3. **刻意不用敏感字段**：种族、宗教、收入、邮编、学校 SAT/学费。产品从聊天记录里也不该推断这些，用它们做匹配也有公平性问题。
4. **机器学习按场次交叉验证**：21 场活动分 5 折，训练和测试的人来自不同场次，同一个人不会同时出现在训练和测试里。
5. **规则基线的权重事先拍定**，不看标签调参。
6. **L1 与 L2-judge 的 prompt 只差“代聊记录”这一块**，两者之差就是代聊带来的增量信息。

## 4. 对比的方法

| 组 | 做法 | 成本 |
|---|---|---|
| B0 随机 | 随机分数 | 0 |
| B1 规则 | 兴趣相关系数 + 双方是否是彼此看重的类型 + 年龄差 + 同专业 | 0 |
| B2 逻辑回归 | 15 个对称的配对特征（见 `lib/features.mjs`） | 0 |
| L1 大模型只看档案 | 裁判读双方档案，给出 A 想再见 B、B 想再见 A 的概率，相乘 | 1 次调用 / 对 |
| L2-self 分身自评 | 两个分身按档案代聊 6 句；各自**只看自己的档案 + 对话**，站在主人角度判断，相乘 | 8 次调用 / 对 |
| L2-judge 档案 + 代聊裁判 | 裁判读双方档案 + 代聊记录（App 里实际使用的匹配分） | 与 L2-self 共用对话，+1 次调用 |

大模型组和 App 调用的是**同一份代码**（`lib/agents.mjs`），只把场景从“交友”切换成“快速约会”。

## 5. 指标

- **主指标**：互选成功的 AUC，分层 bootstrap 2000 次得到 95% 置信区间。
- **配对比较**：所有方法共用同一组重抽样下标，直接计算 AUC 差值的置信区间。
- 辅助：前 20% 命中率（平衡样本下随机水平 50%）、单向意愿 AUC、每对的 token 和耗时。

## 6. 事先定好的判定规则

为了避免看到结果再找说法，判定规则在跑实验之前就写死在 `04_evaluate.mjs` 里：

- L2-judge − L1 的 95% CI **下限 > 0**：代聊带来了增量信息，匹配分可以把代聊作为核心依据。
- 区间包含 0：没有证据表明代聊能提升预测。代聊定位为**体验和破冰功能**，匹配排序主要靠便宜的方法。
- **上限 < 0**：代聊反而引入噪声（例如分身一味附和），需要改分身的 prompt 或去掉这一步。
- 最好的方法 AUC 仍低于 0.62：产品上不展示“契合度 92%”这类精确数字，改为分档表述。

## 7. 当前结果（基线已跑，大模型组待跑）

| 方法 | AUC | 95% CI |
|---|---:|---|
| 随机 | 0.493 | 0.429–0.557 |
| 规则打分 | 0.567 | 0.503–0.632 |
| 逻辑回归 | 0.593 | 0.529–0.658 |

全量 4017 对上：规则 0.566，逻辑回归（按场次交叉验证）0.566。影响最大的特征是年龄差（负）、同专业大类、外出和约会频率。

**已经可以得出的结论**：见面前的信息只能弱预测两人是否来电（AUC 约 0.57–0.59）。这与 Joel、Eastwick、Finkel（2017，*Psychological Science*）用机器学习分析快速约会数据的发现一致：能预测“谁普遍受欢迎、谁普遍爱说 Yes”，但很难预测“这两个人之间特有的化学反应”。
据此，App 已经把“契合度 92%”改成了分档表述（很可能聊得来 / 值得一试 / 可能不太来电）。

大模型组能否突破这个天花板，是接下来要回答的问题。

## 8. 怎么运行

```bash
# 0. 在项目根目录配置密钥
cp .env.example .env.local   # 填入 LLM_API_KEY

# 1-2. 数据准备 + 基线（几秒钟，不需要密钥）
npm run exp:prepare
npm run exp:baselines

# 3. 先跑 20 对试点，检查对话和打分是否正常
npm run exp:pilot
npm run exp:eval             # 看 results/report.md 里的案例

# 4. 跑完整 300 对（可随时 Ctrl+C，重跑会跳过已完成的配对；相同请求走本地缓存，不重复花钱）
npm run exp:llm
npm run exp:eval
```

**预计成本**：每对约 1 万个 token（L1 + L2），300 对共约 300 万 token。按 deepseek-flash 高峰价（每百万 token 输入约 0.30 美元、输出约 1.20 美元）估算，总共不到 1 美元（约 5–8 元，以官网当前价格为准）；错峰运行更便宜。并发 6 时约 20–30 分钟。

**产出**：
- `results/report.md`：完整报告（结论、指标表、两两比较、单向意愿、成本、典型案例、局限）
- `results/results.json`：App 的 `/lab` 页面读取这个文件展示结果

## 9. 局限

- 数据是美国研究生的异性快速约会，SocialQ 是中国年轻人交友，只能作为“见面前信息能否预测见面后互相有兴趣”的代理验证。
- 见面后的决定很大程度取决于外貌和现场感觉，这些不在档案里，任何方法都有天花板。
- 人格卡由问卷模板生成，而不是从聊天记录提炼。本实验验证的是“代聊 + 判断”这一层，不验证“从聊天记录提炼人格”那一层；后者需要另做人工标注评估。
- 同一个人会出现在多对配对里，bootstrap 置信区间会略微偏窄。

## 文件说明

| 文件 | 作用 |
|---|---|
| `01_prepare.mjs` | 清洗数据，生成人员档案、配对和评测集（本地没有原始数据时自动下载） |
| `02_baselines.mjs` | 随机、规则、逻辑回归三个基线 |
| `03_llm.mjs` | 大模型组（L1、L2），支持断点续跑和磁盘缓存 |
| `04_evaluate.mjs` | 指标、bootstrap、自动结论、报告 |
| `lib/survey.mjs` | 问卷字段 → 人格卡（含防泄漏和敏感字段排除） |
| `lib/features.mjs` | 配对特征、规则打分、逻辑回归 |
| `lib/metrics.mjs` | AUC、bootstrap、Top-K |
