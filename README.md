# SocialQ：用几分钟的输入，造一个能替你开口的社交分身

> 概念原型，与腾讯 / QQ 官方无关。候选用户均为虚构人物。

年轻人想认识新朋友，最难的是第一句话。SocialQ 让每个人用很少的输入（几道题、一段对话、或者一段自己的聊天记录），
得到一份**能交互、能交流的社交状态**：它知道你喜欢什么、怎么说话、最近在忙什么、不想聊什么，
并由你的 AI 分身（claw）带着它去和别人、别人的分身交流。聊得来，再由真人接管。

## 核心问题

**SocialQ 要解决的是 context / memory 层的问题：怎样用尽量轻的用户输入，构建一份足够像你、又不含敏感信息的社交状态，让 agent 能拿着它替你交流。**

匹配和破冰是建立在这层之上的应用，不是核心本身。这样定位有两个原因：

1. **匹配预测有天花板。** 我们用真实快速约会数据做的实验显示，只凭见面前的信息预测两人是否来电，AUC 只有 0.57–0.59（见下文）。把产品押在“算得准”上站不住。
2. **“替你把第一句话说出去”不依赖预测准不准。** 只要分身足够像你，它就能降低开口成本；而“像不像你”是可以直接测量和改进的。

难点在于**轻量和保真之间的矛盾**：输入越少，分身越容易千篇一律。SocialQ 的工作就是在这对矛盾里找到最好的平衡。

## 产品流程

```
轻量输入：引导问卷 / 分身访谈 / 可选的聊天记录上传（任意平台）
  → 隐私闸门：只留本人内容 → 脱敏 → 敏感项丢弃
  → 社交状态：自述、兴趣、风格、节律、近况、关系六层；每条有来源、置信度、过期时间和披露级别
  → 分身交流：别人可以直接和你的分身聊；你的分身也可以和别人的分身代聊破冰
  → 真人接管：觉得合适，以真人身份接着聊
  → 反馈回写：本人标“准 / 不准”、熟人辨认、接管结果，回过头修正社交状态
```

## 怎么判断做对了

| 编号 | 问题 | 做法 | 通过标准（示意） |
|---|---|---|---|
| R1 | 社交状态**准不准**？ | 本人逐项给人格卡和近况打“准 / 不准” | 准确率 ≥ 70% |
| R2 | 分身**像不像**本人？ | 熟人辨认：给朋友看几段代聊，让 TA 找出哪段是你的分身 | 辨认正确率显著高于随机猜 |
| R3 | 输入**够不够轻**？ | 比较问卷、访谈、聊天上传三种输入，各要花几分钟才能让 R1、R2 达标 | 5 分钟以内的输入能达标 |
| R4 | 分身交流**有没有用**？ | 小范围试验里统计真人接管率，以及接管后 3 天仍在聊天的比例 | 接管率 ≥ 20%，3 天仍在聊 ≥ 30% |

R1–R3 衡量社交状态这一层本身，是现在最优先的验证；R4 衡量建在它上面的破冰应用。

## 已有证据：匹配预测实验

我们用哥伦比亚大学快速约会实验的真实数据（4017 对约会，标签是双方是否都想再见面）检验“见面前的信息能不能预测来不来电”。详细设计见 [`experiments/speed-dating/README.md`](experiments/speed-dating/README.md)。

| 方法 | AUC | 95% CI |
|---|---:|---|
| 随机 | 0.493 | 0.429–0.557 |
| 规则打分 | 0.567 | 0.503–0.632 |
| 逻辑回归 | 0.593 | 0.529–0.658 |
| 大模型只看档案 / 代聊后自评 / 档案 + 代聊裁判 | 待运行 | `npm run exp:pilot` → `npm run exp:llm` → `npm run exp:eval` |

**这个结果直接促成了这次定位调整：**

1. **不展示“契合度 92%”**，只给三档：很可能聊得来 / 值得一试 / 可能不太来电，并附理由和风险点。
2. **核心从“匹配”转向“社交状态”**：匹配排序用便宜的方法（兴趣重合度）就够，资源投在让分身更像本人上。
3. 实验保留下来，作为**回归检查**：以后改了 prompt 或社交状态的格式，重跑一遍，确认分身判断没有变差。大模型组跑完后，也能回答“代聊是否带来档案之外的信息”。

## 技术架构

核心是一个和平台无关的**社交状态层**，其他部分都是它的输入或使用者。

```
输入适配器（问卷 / 访谈 / 各平台聊天导出）
        │
        ▼
   隐私闸门（lib/privacy.mjs）
        │
        ▼
   社交状态层：读、写、检索、过期、披露级别过滤        ← 本人修改、标“准 / 不准”
        │
        ▼
   分身运行时（lib/agents.mjs）：每次对话时读取社交状态 → 调用大模型 → 回写关系和待确认的近况
        │
        ├── 和某人的分身直接聊天
        ├── 分身之间代聊破冰（匹配是其中一种用法）
        └── 熟人辨认等评估任务
```

几个关键决定：

- **分身是数据，不是常驻程序。** 每个用户的分身就是数据库里的一行配置加上它的社交状态，所有人共用同一套代码；需要说话时才读取记忆、调用一次模型。
- **社交状态分六层。** 自述、兴趣、风格、节律四层相对稳定，每次都带上；近况层是一条条带过期时间的结构化 case，按话题只取相关的几条；关系层记录和每个人聊过什么。
- **存结论，不存原文。** 原始聊天记录只在内存里处理，入库的只有提炼后的结论和不超过 20 字的本人原话证据。
- **四级披露。** 公开 / 匹配可见 / 仅自己的分身 / 不存。分身只说当前级别允许的内容。
- **人格卡只追加版本、不覆盖。** 每次对话都记下当时用的版本、prompt 版本和模型，评估结果才能追溯。

当前代码实现了这条链路的最小版本（人格卡一次生成、存在浏览器里）；持久化存储、近况 case、披露级别、分身直接对话和评估任务是下一步要补的。

## 快速开始

```bash
npm install
cp .env.example .env.local   # 填入 DeepSeek 密钥（不填也能跑，自动进入演示模式）
npm run dev                  # 打开 http://localhost:3000
```

- 没有密钥时，页面会显示“演示模式”，用关键词规则模拟大模型输出，方便离线演示。
- 模型走 OpenAI 兼容接口，改 `.env.local` 里的 `LLM_BASE_URL` 和 `LLM_MODEL` 就能换成通义千问、Kimi 等。

## 隐私与安全设计

| 风险 | 做法 | 代码 |
|---|---|---|
| 聊天记录里有对方的个人信息 | 只保留本人发出的消息，对方的消息在发给模型前丢弃 | `lib/privacy.mjs` |
| 手机号、邮箱、身份证、QQ 号等 | 发给模型前正则脱敏 | `lib/privacy.mjs` |
| 模型推断敏感属性 | prompt 明确禁止推断性别、年龄、民族、宗教、政治、健康、性取向、学校、住址 | `lib/agents.mjs` |
| 人格被“瞎编” | 每项特质必须附原话证据，没有证据就标“证据不足”；用户可删除标签 | `lib/agents.mjs`、`app/page.js` |
| 用户以为在和真人聊 | 代聊气泡全程标注“AI 代理”，真人接管后界面切换 | `app/chat/page.js` |
| 未成年人陌生人社交 | 18+ 确认，服务端也校验 | `app/api/persona/route.js` |
| 分身泄露隐私 | 分身 prompt 禁止透露联系方式、住址、学校名称 | `lib/agents.mjs` |
| 原始聊天被保存 | 只在请求内存中处理，不落盘、不打日志 | `app/api/persona/route.js` |
| 零散信息拼起来认出一个人 | 近况只存粗粒度的时间和地点；每次对话只取少量相关条目（计划中） | — |

## 代码结构

```
lib/                     App 和实验共用的 AI 核心
  llm.mjs                OpenAI 兼容客户端（重试、JSON 模式、mock 回退）
  agents.mjs             人格提炼、Agent 代聊、分身自评、中立裁判、分档
  persona.mjs            人格卡结构、渲染、兴趣重合度（将扩展为六层社交状态）
  privacy.mjs            本人消息过滤、脱敏
  samplePool.mjs         虚构候选用户
  mock.mjs               演示模式
app/
  api/persona/route.js   聊天记录 → 人格卡
  api/match/route.js     粗筛 → 代聊 → 判断
  page.js / mixer / chat / lab
experiments/speed-dating/  匹配预测实验（现作为回归检查）
```
